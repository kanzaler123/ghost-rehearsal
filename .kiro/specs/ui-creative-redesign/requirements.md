# Requirements Document

## Introduction

Ghost Rehearsal lets an organiser model an event flow, rehearse it with simulated guests before the real event, and compare how the same guests fare under two arrangements. The owner finds the current interface ordinary, without a memorable identity, and below the level expected of a competition entry. This feature is a complete UI/UX redesign and its implementation, delivered for review on its own branch.

The owner delegates the creative direction. This document fixes the outcomes, the evidence and the behaviour that must survive. It does not prescribe a visual style, colour, layout, component or library; the design phase decides those, and the implementation proceeds without asking the owner to choose between them.

The owner's target outcomes are:

- a distinct visual identity at first sight;
- a core working interface worth remembering;
- a product whose purpose users understand and whose operations they complete without friction;
- an intuitive, continuous presentation of the simulation and of plan differences;
- the same level of finish across pages and states, fit for real use and for demonstrations.

**Scope.** The main effort goes into the surfaces users operate: organising and editing the flow and its stations; configuring parameters and starting a run; showing guests arriving, moving, queueing, being served and finishing; comparing and replaying two plans and understanding the results; and moving between editing, running and comparing. The entry screen, guided demo, dialogs, panels and the empty, computing, error, stale and completion states use the same design language. Inside the Owned_Area the front end may be restructured freely, without keeping the old page layout. The simulation algorithm, replay computation, statistics, comparison rules, stale rule, project file and persistence formats, Worker protocol and the other product rules stay unchanged; a change that the design would need is recorded as a request instead (Requirements 16.8 and 22).

**Collaboration boundary.** On 2026-11-16 the owner set the boundary for this round. Independent Parallel_Branches handle project reliability, simulation performance, replay computation, import fault tolerance and browser tests. The Redesign owns `src/app/App.tsx`, the existing `src/components/**`, the Stylesheets, the visual assets and the page interaction structure; the Glossary defines this Owned_Area by path. It keeps the Business_Contracts and makes no change to the simulation algorithm, the persistence format or the Worker protocol. It stays in the current Workspace on the Work_Branch, preserves uncommitted work that is not its own, leaves the Draft_PRs unmerged, records every interface change for the Integration_Session and stops at a reviewable Work_Branch, with no merge into `main` and no deployment. Integrating the Work_Branch with the Parallel_Branches and the Draft_PRs is out of scope; a separate Integration_Session does that after the hand-off (Requirement 22).

## Requirements
