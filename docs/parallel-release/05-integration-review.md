# E：统一集成、独立 review 与发布验收

此任务在 A/B/C/D 各自可评审后启动。先阅读 [公共规则](README.md)。从当时的 `kiro/release-integration` 创建新的 `kiro/release-verification` 工作分支；不要现在从旧 main 提前开一个与将来集成状态脱节的验证分支。

## 1. 分支 review 门槛

每个任务 PR 的 base 必须为 `kiro/release-integration`。独立 reviewer 阅读 diff、任务验收、实际运行结果及浏览器证据，指出具体阻塞项。实现会话的自评与 CI绿灯不能代替独立 review。

阻塞项至少包括：数据/单位/统计人群错误、覆盖用户数据、焦点或主操作无法到达、假结果/假证据、关键功能入口缺失、基线回归、无法构建、未处理的并行文件冲突。优先级较低的改进明确列为后续，不假称全部规格验收。

只有对应分支的阻塞项解决并复核后才汇入集成分支。可以按 A测试准备→B→A业务→D模块→C模块顺序，具体以 review 完成情况调整；D/C先在独立lab完成模块评审。

## 2. 冲突处理与历史

保留各任务提交和贡献归属。禁止通过选择整个 ours/theirs 文件来省略另一项工作。每个冲突先列出两边用户行为与接口，再合并最小逻辑，并运行受影响的回归。

公共日志保留真实条目并去重；把 `docs/kiro/*` 汇总到根 KIRO_USAGE 时清楚写明 Kiro、人工与其他工具贡献。不能把任务计划或原有Codex成果写成Kiro新增成果。

如 main 在此期间前进，先把当前 main 合入集成分支、核对差异，再对最终候选执行验收。记录最后实际验证的完整 commit SHA。

## 3. 主工作台装配

E作为唯一接线负责人，可修改 App、Dialogs、Inspector、共享文案/样式及必要适配层。

### C 接线

- 在比较工作流中提供可发现的“稳健性试验”入口，接收当前活动及选中的方案。
- 保留单次比较与实验台的区别；实验台固定cutoff并清楚显示，不继承一个看不见的final开关。
- 批次使用开始时的项目快照；记录当前输入是否已变化。不要在运行中悄悄切换数据。
- 正常预演与批次仿真的同时运行策略明确；关闭/卸载实验台能够取消并释放其Worker。
- 单组导出能在普通工作台重新打开；资源、方案ID与场景引用合法。

### D 接线

- 在ScenarioEditor的具体到达群体中嵌入ArrivalDataEditor；局部应用只改外层草稿，最终Apply才提交项目。
- 在Inspector服务参数中嵌入ServiceDataEditor和来源控件；一组导入作为一次可撤销修改。
- 手工改动既有数值输入时，调用D的来源更新helper，保留说明并显式处理来源标签变化。
- 共用B的Modal/Field/数字草稿语义，校验错误不能绕过外层保存。
- 导入、导出、draft recovery、stale检测、共享场景与中英文路径连通。

### A/B 协调

- 检查弹窗中全局快捷键，尤其Ctrl/Cmd+S，不能把尚未应用的无效草稿误表示成已保存。
- 检查比较全屏人物视图、引导与Modal叠加时，焦点只到可见操作。
- App中的模板/保存/重命名对话框虽然未由B直接修改，也必须享受B的滚动与焦点行为。

## 4. 真实浏览器发布门槛

用实际production build与`/ghost-rehearsal/`子路径，不只测试dev根路径。执行真实Worker、文件选择/下载与浏览器存储，不替换React hooks或把测试数据塞进应用状态绕过UI。

| 路径 | 最低验收 |
| --- | --- |
| 初次进入/示例 | 示例可运行；流程居中，关键内容可见；后续手动视口不被延迟自动定位抢回 |
| A/B/C演示 | 总览、分组、人物、03:30首次差异、证据、创建C、代价与导出一致 |
| 统计切换 | 阈值、人群、cutoff/final、缺失/过期、名单与人数一致 |
| 方案归属 | 从B编辑/删除只作用于B；B失败抽屉能定位B |
| 弹窗与表单 | 无效导入叠层、一次Escape一层、恢复焦点、数值重输、tabs、短屏底部按钮 |
| 实测参数 | 两类CSV、预览/错误/取消/应用、共享场景、来源、过期与重跑、JSON往返 |
| 稳健性 | 配置、真实批次、取消/重跑、所有结果/有效分母、单组复现 |
| 保存与模板 | draft恢复、手动保存、项目/模板导入导出，失败保留原内容 |

Chromium桌面和390×844作为主要PR检查；关键表单另测390×568。中英文各覆盖至少一条完整导入/验证/关闭路径。最终对另一浏览器做关键流程验证；若环境无法执行，明确记录未覆盖，不能写跨浏览器认证。

失败时保留截图、trace、console/pageerror、视口与语言。使用状态等待；不靠提高超时、重试次数或删除断言掩盖问题。PR保留typecheck、单元测试、build；main部署必须依赖浏览器检查通过，普通PR不执行部署。

## 5. 性能检查与必要修复

基线生产主JS约829.66kB（gzip255.71kB），这是体积提示，不是已证实的交互性能故障。最终测量首屏可操作时间、预演、切换旅程、批次进度/取消，在记录的浏览器与视口下给出结果。

若新增实验/导入面板使初始加载明显变差，在E中按功能入口使用合适的动态导入；验证子路径Worker与样式加载。不要单纯调高warning阈值作为优化成果，也不要为可逆的小调整扩展一整套无关测试。

## 6. 材料定稿

基于最终已验证候选更新README、双未来总览/同人旅程真实截图、英文A/B/C案例、参数导入说明、稳健性结果解释、英文Kiro使用说明和不超过三分钟的演示稿。

如无真实组织者或真实场地数据，继续明确区分合成演示、软件验证与真实活动效果；不得补写访谈或实测结论。公开视频与Devpost发布由用户按其提交安排处理，文件草稿不等于已经发布。

## 7. 最终统一合入 main

1. 完成`docs/reviews/release-verification.md`，记录候选SHA、已审分支、实际验证、残留限制。
2. E的接线/修复PR通过review后进入集成分支。
3. 对集成分支最终tip运行适当的完整发布验收，确保被review的代码就是拟发布代码。
4. 创建唯一的`kiro/release-integration → main`发布PR，说明用户行为变化、各任务来源、验证与限制。
5. 独立review确认阻塞项清零及CI通过后统一合并，检查该main提交的Pages部署与线上核心路径。

在这五步完成之前，保持main为现有稳定版本。不要把某个独立分支的测试结果冒充整个集成版本的结果。
