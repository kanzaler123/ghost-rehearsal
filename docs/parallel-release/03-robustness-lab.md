# C：多种子与多条件的稳健性实验台

分支：`kiro/robustness-lab`。先阅读 [公共规则](README.md)。这是产品增强；验收目标是公平配对、可重复计算和完整呈现，不是让某个方案在所有条件下获胜。

## 目标

对同一活动的两个或三个既有方案，按事先列出的种子和服务时长条件重复运行，让用户判断结果对假设的敏感程度。交付真实 Worker、可操作面板、独立评审入口、逐次结果和可复现导出。

本轮固定 cutoff 口径，使用相同观察窗口。不得把不同种子的同 ID 访客当成同一个人，也不得把 final 与 cutoff 混在一个结果分布中。

## 独占文件与评审入口

新增 `src/experiments/robustness/`，建议拆分 types、conditions、summarize、aggregate、runner、worker、client、RobustnessPanel、局部 CSS/labels 与 lab 挂载文件。

新增 `labs/robustness.html`，在现有 `npm run dev` 后从 `/labs/robustness.html` 打开真实面板。新增 `tests/robustness-*.test.ts`、`e2e/robustness/`、`docs/robustness-contract.md`、独立 Spec/review/usage 文件。

不改 App、现有比较组件、simulation/schema、analysis/project、全局 CSS/messages、依赖锁、Vite 和 CI。导入现有 `simulate`、类型和校验即可。开发用 lab 是评审入口；主应用接线与最终部署验收由 E 完成。

## C1：输入与条件

面板接收合法 `ProjectDocument`，选择基线和一到两个候选；所有方案必须引用同一 Scenario。默认载入现有 Open House A/B；允许从合法项目 JSON 读取已存在的 C，不另写创建 C 的业务。

默认种子明确列为 `20261114` 到 `20261123` 共 10 个。默认条件为原始、服务时长额外 ×1.25、额外 ×1.5。两个方案共 60 个单次仿真；启动前显示精确数量。首轮总量上限设 200 jobs，说明这是资源保护配置，不是性能认证。

种子遵守当前 Schema 整数范围；重复种子需明确报错或由用户确认去重，不能重复计为独立试验。校验空候选、重复方案、跨场景、非法图和倍率边界。

条件变换是相对原场景：

- 原始条件保留原 overrides。
- 如原全局倍率为 1.2，额外 ×1.25 后应是单个全局倍率 1.5。
- 保留按 stageKey 的倍率、资源中断、到达、路线、班次和来源。
- 超过 Schema 上限明确拒绝，不偷偷截断。
- 每个 seed × condition 的全部方案使用相同的变换后 Scenario。
- 所有输入保持不变，使用快照/复制处理派生请求。

## C2：单 Worker 顺序运行与真正取消

复用 `simulate(RunRequest)`，不要实现第二套仿真。每完成一个 job，提取紧凑摘要和进度，再释放该次完整运行的引用。不要向主线程传回每次完整 events，也不要保留几十份全部轨迹。

每行摘要至少包含：batchId、job标识、seed、condition、planId、status、modelVersion、inputKey、scenarioKey、coveredUntil、statisticsUntil、全部 outcomes、arrived、平均/P90/总等待、员工/设备数量、issues。失败时指标为 null，不是 0。

`simulate` 是同步函数，因此仅给忙碌 Worker 发送 cancel 消息不足以保证及时取消。客户端取消调用 `worker.terminate()`，保留已经收到的摘要，将未完成/未运行项目明确标记，批次显示部分结果。下一次启动创建新 Worker；用 batchId 屏蔽迟到消息；卸载面板时终止 Worker。

区分仿真 succeeded/failed/aborted 与客户端 canceled/not-run。达到事件上限的结果不得当作完整成功样本参与改善统计。

## C3：成对聚合

配对键为相同 seed、condition、统计范围下的 baseline/candidate。每个候选单独计算有效配对数：B 某次失败不能抹掉该次合法的 A/C 配对。

每个条件、每个候选至少展示：

- 完成、未完成、提前离开人数的成对变化。
- 每次运行的平均等待变化与 P90 变化：中位数、最小值、最大值。
- 完成更多/相同/更少的次数；平均等待减少/相同/增加的次数。
- 有效配对数 / 计划配对数；失败、中止、取消及未运行数量。
- 员工、设备和对应统计窗口内资源成本信息，时间单位明确。

等待均采用当前 run.statistics 的全部已到达口径。提前离开应沿用现有 outcome 定义，明确包括哪些状态，不另建含糊的成功/失败分类。

不得把各次 P90 求平均后称为“总体 P90”，不得把失败补零，也不得仅挑选有利 seed。单个“最优方案分数”、置信区间和显著性结论不在本轮输出中。

## C4：交互与导出

1. 配置区：项目/方案、种子、条件、预计运行次数、开始。
2. 运行区：当前条件和 seed、进度、成功/失败数、取消。
3. 结果区：按条件与候选分组的摘要，完整逐次表，正负变化并列。
4. 筛选区：条件、候选、状态；筛选不影响导出的完整原始结果。
5. 完整 JSON 导出：输入项目快照或等价的完整场景/方案快照、条件变换规则、全部种子、全部 job 摘要、模型版本、运行配置、状态。单有 fingerprint 不足以复现输入。
6. 导出单个 seed × condition 的合法项目 JSON，可由现有工作台导入，复现那一组方案；保持共享场景引用完整。
7. 未完成批次可以导出，文件和界面都清楚标为 partial。
8. 本模块不写工作台 localStorage。与主工作台接线时，由 E 负责入口、运行互斥/取消和快照过期提示。

中英文与局部 CSS 在本模块维护。390px 宽度下，配置、开始/取消、摘要和结果表都能操作；宽表在自己的区域滚动。

## C5：必须验证的固定结果与边界

原 Open House，seed=20261114、原始条件、cutoff=1800秒：

| 指标 | A | B |
| --- | ---: | ---: |
| 完成 | 43 | 41 |
| 未完成 | 253 | 253 |
| 提前离开 | 4 | 6 |
| 平均等待秒 | 1057.716666… | 1055.333333… |
| P90等待秒 | 1547.143 | 1547.143 |

可用已有增配人员 fixture 验证 C：完成72、未完成218、提前离开10、平均等待954.083333…秒、P901444.286秒、工作人员4。读取真实运行，不写死显示数字。

其他必要验收：

- 同配置重跑的指标与指纹一致；时间戳等非确定性元数据单独说明。
- 调换种子、条件、方案输入顺序不改变对应结果和汇总。
- 克隆相同方案作为候选，合法配对的所有变化为零。
- 无到达者时等待为 null，数据不可得不会被解释为零等待。
- 失败候选不影响其他合法候选配对；全部失败仍有完整失败清单。
- 原有倍率、工序倍率与中断保持；变换不污染原项目。
- 取消、立即重跑、卸载、迟到消息，状态和结果隔离正确。
- 确定性数据换 seed 得到零范围是允许结果，不包装成多次真实世界观测。
- 独立 lab 使用真实 Worker，页面可以响应取消和筛选。
- 导出的单组项目在原工作台重跑，结果与批次摘要一致。
